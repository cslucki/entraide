## 1. Schéma du pipeline actuel

```
LoopChat::sendMessage()  [@tous, propriétaire/animateur uniquement]
  └─ LoopMessageService::sendUserMessage()           [1 transaction]
       ├─ LoopMessage::create()                      [1 insert]
       └─ notifierLesMentions($destinataires)
            ├─ User::whereIn(...)                    [1 select, tous les destinataires]
            ├─ NotificationPreferenceResolver::allowsMany()
            │    └─ 3 requêtes au TOTAL, quel que soit N          ← déjà optimisé (TASK-1797/1778)
            └─ POUR CHAQUE destinataire :
                 └─ NotificationEmitter::emit()
                      ├─ MemberNotification::create()            [1 insert]
                      └─ NotificationDeliveryPlanner::plan()
                           ├─ canal EMAIL  → MemberNotificationDelivery::create() [1 insert]
                           │                 → dispatch(SendNotificationEmail)    [sync ⇒ exécuté ICI]
                           └─ canal WEB_PUSH → idem, SendNotificationWebPush

SendNotificationEmail::handle()  →  NotificationEmailDeliverer::deliver()
  ├─ MemberNotification::find() + MemberNotificationDelivery::find()   [relecture, cf. §4]
  ├─ prendre()                     [1 update atomique pending→sending]
  ├─ livrer()
  │    ├─ organization_id du destinataire, RELU                       [1 select]
  │    ├─ NotificationPreferenceResolver::allows()  (préférence COURANTE, volontaire — §6)
  │    ├─ NotificationTargetResolver::resolve()
  │    │    ├─ tenant du destinataire, RELU À NOUVEAU                 [1 select — doublon]
  │    │    ├─ LoopMessage → Loop  (chemin OBJECT_LOOP_MESSAGE, NON passé par ScopedReadCache)
  │    │    └─ appartenance active                                    [1 select]
  │    └─ envoyer()
  │         ├─ rendreDepuisGabarit()  →  LoopMentionMailer::compose() ×2 (réel + expurgé)
  │         │    chaque appel, INDÉPENDAMMENT :
  │         │      Loop::first()  +  Organization::first()  +  SystemEmailTemplateResolver::resolve()
  │         │      (cascade 5 crans) + EmailerService::availableVariables($acteur)
  │         ├─ Mail::html(...)                                        [SMTP, hors SQL]
  │         └─ transaction : email_logs::create() + livraison::save() [2 écritures]

SendNotificationWebPush::handle()  →  NotificationWebPushDeliverer::deliver()
  même structure, SA PROPRE relecture du tenant, SA PROPRE résolution de cible.
```

**Le chemin complet, par destinataire, traverse donc deux livreurs indépendants
(email, web push) qui ne partagent RIEN entre eux ni avec le producteur** —
chacun relit le tenant, chacun relit (ou tente de relire) la cible, chacun
compose/résout séparément. C'est la structure voulue pour un VRAI worker
asynchrone (résilience au rejeu, aucun état partagé entre unités de travail
indépendantes) — et c'est exactement ce qui devient coûteux quand
`QUEUE_CONNECTION=sync` fait exécuter les deux livreurs, pour chaque
destinataire, **dans la même requête HTTP**.

Mesuré sur le jumeau QA `bouclepro_prod_work` (PostgreSQL), MailHog exclusif,
`QUEUE_CONNECTION=sync`, **un processus PHP isolé par point de mesure** (voir
note méthodologique ci-dessous). Boucle dédiée, membres synthétiques
`bench1798-N-*@bouclepro.test`, entièrement nettoyés après chaque mesure.

| 1  | 52    | 49,4 ms    | 50,1 ms    | 67,7 ms   | 167,1 ms  | 1  | 1  | 1  | 42,5 Mo |
| 5  | 229   | 145,0 ms   | 216,6 ms   | 105,7 ms  | 467,4 ms  | 5  | 5  | 5  | 42,5 Mo |

**Coût marginal par destinataire additionnel** (régression linéaire sur les 5 points) :
**≈ 44,0 requêtes SQL, 24,1 ms SQL, 44,0 ms SMTP, 12,0 ms PHP, 80,1 ms au total.**
Coût fixe (indépendant de N, mesuré ≈ 87 ms) : création du message, `allowsMany()`, événement.

Projection à 50 destinataires réels (comme TASK-1797, §4 de son TASK file) :
87 + 80,1 × 50 ≈ **4 092 ms**, cohérent avec la mesure indépendante de
TASK-1797 (4 340 ms pour 50 destinataires réels, méthodologie différente) —
les deux mesures se **corroborent**.

**Répartition du temps total à N=49 : SQL 30 %, SMTP 54 %, PHP 16 %.**
C'est le fait le plus important de cet audit : **la majorité du temps n'est
pas du SQL.** Une optimisation SQL parfaite ne peut réduire le temps total
que d'environ 25 à 30 % au mieux ; le reste (SMTP synchrone) n'est réductible
qu'en sortant du mode synchrone — voir §9.

### Note méthodologique — 50 membres ≠ 50 destinataires, et le piège du processus partagé

- **« N destinataires »** = N membres actifs AUTRES que l'auteure, qui reçoivent
  réellement une notification. L'auteure est elle-même un membre actif
  supplémentaire (jamais notifiée) : une Boucle à « 50 destinataires » compte
  donc **51 membres actifs au total** — c'est la même convention que
  TASK-1797 et son constat de performance initial.
- **Piège mesuré, corrigé avant de produire ce tableau** : une première
  version du banc exécutait les 5 scénarios à la suite, dans UN SEUL
  processus PHP. Les comptes de requêtes croissaient alors de façon
  anormale (ex. la requête `loops` passait de 4/destinataire à 20/destinataire
  entre le premier et le cinquième scénario) — signe d'une contamination
  entre scénarios dans le banc lui-même (très probablement liée aux
  singletons `scoped()` du conteneur, qui ne se réinitialisent qu'entre deux
  **requêtes HTTP** ou deux **jobs de file réelle**, jamais entre deux appels
  directs dans un même script CLI). **Chaque point du tableau ci-dessus a
  donc été mesuré dans un processus PHP dédié**, ce qui élimine cet artefact
  — confirmé par la cohérence parfaitement linéaire des comptes de requêtes
  par type (ex. `loops` : exactement 4 × N à chaque palier).

## 3. Les cinq principales sources de coût, classées

| # | Source | Part estimée | Nature |
|---|---|---|---|
| 1 | **SMTP synchrone, un envoi à la fois** (~44 ms/destinataire, 54 % du temps total) | La plus grosse | Structurelle — nécessite un dispatch asynchrone réel pour être réduite (§9) |
| 2 | **Gabarit mailer rendu DEUX FOIS par destinataire**, sans partage (`LoopMentionMailer::compose()` appelé une fois pour l'envoi réel, une fois pour la copie expurgée — chacun recharge Loop, Organization, résout le template depuis zéro) | ~8-10 requêtes/destinataire | Logique locale, zéro risque de cache |
| 3 | **Absence d'extension de `ScopedReadCache` au chemin `loop.mention.created`** (Loop, Organisation, LoopMessage, auteur — identiques pour tous les destinataires d'un même message, mais rechargés individuellement) | ~10-15 requêtes/destinataire | Mécanisme déjà prouvé (TASK-1778) sur `loop.help_request.created`, jamais étendu aux mentions |
| 4 | **Vérification d'appartenance d'Organization répétée indépendamment** par `NotificationEmailDeliverer::livrer()`, `NotificationWebPushDeliverer::livrer()` ET `NotificationTargetResolver::resolve()` pour le MÊME destinataire | ~6 requêtes/destinataire | Logique dupliquée entre 3 endroits distincts |
| 5 | **Relation différée `$user->organization`** dans `EmailerService::availableVariables()`, rechargée pour le même acteur à chaque rendu (2×/destinataire) | ~2 requêtes/destinataire | Eager-loading manquant |


**Lecture, par destinataire (÷10) :**
- 6× la même vérification « ce destinataire est-il encore dans cette
  Organization ? », répartie entre les deux livreurs et le résolveur de
  cible — un seul suffirait par livreur.
- 5× `organizations`, 4× `loops`, 2× `loop_messages` (deux variantes de la
  MÊME ligne : une pour `NotificationTargetResolver`, une pour
  `rendreDepuisGabarit()`) — **toutes identiques pour les 10 destinataires**
  et pour les deux appels (réel + expurgé) à l'intérieur d'un même
  destinataire.
- 2× `system_email_templates` (cascade de résolution) — doublé parce que le
  gabarit est résolu deux fois (réel + expurgé) alors que c'est **la même
  ligne** les deux fois.

Ces chiffres sont des **mesures directes**, pas des extrapolations : le
fichier brut (`DB::listen`, requêtes normalisées) est reproductible avec le
script de banc conservé dans ce TASK (voir Handoffs).

## 5. Optimisations possibles, gains estimés — mesures vs hypothèses

| Piste | Description | Gain | Statut |
|---|---|---|---|
| **A1 — partager le gabarit résolu entre les deux rendus** | `GabaritEmail`/`LoopMentionMailer::compose()` résout `SystemEmailTemplate` UNE fois, rend le corps réel ET le corps expurgé à partir du MÊME objet déjà en mémoire. Aucun état partagé entre destinataires, aucune question de fraîcheur. | **MESURABLE directement** : supprime 1-4 requêtes/destinataire (cascade de résolution ÷2) | Hypothèse d'ingénierie forte (lecture du code), pas encore mesurée isolément |
| **B1 — étendre `ScopedReadCache` au chemin mention** | Même mécanisme que TASK-1778 pour `loop.help_request.created` : mémoriser Loop, Organization, LoopMessage et l'acteur le temps d'UNE unité de travail, clé incluant TOUJOURS `organization_id`. | **Hypothèse, calibrée sur un précédent mesuré** : TASK-1778 avait mesuré une division par ~4 des lectures de référence sur un chemin comparable | Nécessite une mesure dédiée après implémentation — le même banc (ce TASK) sert de comparateur avant/après |
| **C1 — eager-load `organization` sur l'acteur** | Charger `$acteur->load('organization')` une fois avant la boucle d'interpolation, au lieu de laisser la relation différée se redéclencher à chaque rendu. | **MESURABLE directement** : -2 requêtes/destinataire | Faible risque, zéro question de cache inter-destinataire |
| **D1 — fusionner la vérification de tenant livreur/resolver** | Les deux livreurs ET le resolver de cible vérifient indépendamment la même appartenance. Un seul passage, partagé à l'intérieur d'un même livreur, suffit. | **Hypothèse** : -2 à -4 requêtes/destinataire | Risque plus élevé — touche un chemin de sécurité PARTAGÉ par toutes les clés de notification, pas seulement les mentions (voir §6) |
| **E — dispatch asynchrone réel** | Sortir l'envoi email/push du cycle de requête HTTP. | **Le plus gros gain possible (~54 % du temps total)** | **Hors mandat de cette TASK** — nécessite un arbitrage d'infrastructure (worker Laravel Cloud), voir §9 |

**Gain combiné réaliste pour A1+B1+C1 (sans toucher D1 ni E), en hypothèse
d'ingénierie et non en mesure directe** : réduction du volume SQL d'environ
44 à 15-20 requêtes/destinataire (-55 à -65 %), soit, au ratio temps/requête
mesuré ici (~0,55 ms/requête), un gain d'environ 13-15 ms sur les 80 ms de
coût marginal par destinataire — **environ 15-18 % de réduction du temps
total ressenti**, le poste SMTP restant inchangé. Ce chiffre sera soit
confirmé soit corrigé par une remesure avec le même banc après
implémentation ; il ne doit pas être présenté comme acquis.

## 6. Risques techniques et fonctionnels

- **`ScopedReadCache` a une règle stricte, déjà écrite et déjà payée par
  TASK-1778** : jamais une préférence, jamais une appartenance, jamais un
  statut de livraison, **jamais du contenu administrable** (le gabarit
  d'email lui-même a été mis en mémoire puis RETIRÉ, précisément pour cette
  raison — voir le docblock de `SystemEmailTemplateResolver::resolve()`).
  Toute extension à B1 doit se limiter à Loop/Organization/LoopMessage/auteur
  — jamais au `SystemEmailTemplate` résolu, qui reste du contenu
  administrable modifiable en cours de requête par l'écran
  `/admin/system-email-templates`.
- **D1 touche un chemin partagé par TOUTES les clés de notification**
  (`LOOP_HELP_REQUEST_CREATED`, `LOOP_MEMBER_ADDED`, `LOOP_JOIN_REQUEST_CREATED`,
  les commentaires de blog/entraide, les propositions de transaction…), pas
  seulement les mentions. Toute modification de
  `NotificationEmailDeliverer`/`NotificationWebPushDeliverer`/`NotificationTargetResolver`
  doit être revérifiée contre l'ensemble de ces clés, pas seulement
  `TASK1797MentionAllTest`.
- **Les préférences restent lues au moment de la livraison, jamais
  mémorisées** — garantie non négociable déjà en place, à ne jamais toucher
  en poursuivant A1/B1/C1.
- **SQLite et PostgreSQL** doivent rester mesurés séparément : le ratio
  SQL/SMTP observé ici (PostgreSQL local, latence réseau quasi nulle) peut
  différer sensiblement en PROD (Neon) ou sous SQLite (CI), où le coût
  relatif d'une requête réseau est plus élevé — une optimisation qui
  « gagne peu » localement peut gagner davantage en PROD.
- **Idempotence et absence de doublon** (anti-rejeu via `event_id`
  déterministe) ne sont touchées par AUCUNE des pistes A1-D1 : elles vivent
  dans `NotificationEmitter`, non concerné par cet audit.

## 7. Plan d'implémentation en micro-séquences (pour une TASK future, non lancée)

1. **A1** — fusionner les deux rendus de gabarit (réel + expurgé) pour ne
   résoudre `SystemEmailTemplate` qu'une fois par destinataire. Testable
   isolément, zéro risque de cache.
2. **C1** — eager-load `organization` sur l'acteur avant la boucle
   d'interpolation, dans `LoopMentionMailer` et tout mailer partageant le
   même motif.
3. **B1** — étendre `ScopedReadCache` (clé TOUJOURS préfixée par
   `organization_id`) à Loop/LoopMessage pour `loop.mention.created`, en
   copiant exactement le modèle déjà validé dans
   `NotificationTargetResolver`.
4. **Remesure** — rejouer ce même banc (script conservé), aux mêmes 5
   paliers, comparer point par point AVANT/APRÈS. Document de preuve avant
   toute PR.
5. **D1, séparément, dans sa propre PR** — fusion des vérifications de
   tenant, avec revue dédiée et exécution de la suite complète des clés de
   notification partagées (pas seulement les mentions).

## 9. Arbitrages Laravel Cloud

Le gain structurel le plus important identifié dans cet audit (~54 % du
temps total, le poste SMTP) **n'est accessible qu'en sortant du mode
synchrone** : soit un worker de queue dédié (Laravel Cloud en propose,
coût additionnel), soit un mécanisme de traitement différé. C'est un
arbitrage **explicitement hors mandat de cette TASK**, à soumettre
séparément à MASTER si la latence perçue à l'échelle de 49-50 destinataires
reste un problème après les optimisations SQL A1/B1/C1 — celles-ci
plafonnent autour de 15-18 % de gain sur le temps total, jamais davantage
tant que l'envoi reste synchrone.

---

## Conclusion

Le pipeline existant est **fonctionnellement correct** (préférences
respectées, isolation d'Organization, anti-doublon, idempotence — rien de
cela n'est remis en cause). Son coût, à l'échelle de `@tous`, est dominé
par deux choses distinctes : des relectures SQL redondantes de données
identiques pour tous les destinataires d'un même événement (30 % du temps,
réductible de façon mesurable et à faible risque), et le temps d'envoi SMTP
synchrone lui-même (54 % du temps, structurel, hors mandat).

**STOP après ce rapport d'audit. Aucun changement de code applicatif,
aucun merge, aucune modification PROD.**
