## 3. Verdict de performance, complete (point 4 de l'arbitrage)

### A. Les SAVEPOINT, maintenant comptes

Ils ne l'etaient pas : `Connection::createSavepoint()` passe par
`$pdo->exec()` en direct, donc `DB::listen` ne les voit pas. Ils sont desormais
comptes par les evenements de transaction, emis a tous les niveaux.

**Correction d'une estimation precedente** : un commit imbrique n'emet **aucun**
`RELEASE SAVEPOINT` — il decremente un compteur en PHP. Le cout est donc de
**1 aller-retour par transaction imbriquee**, pas 2. J'avais annonce « +4 par
destinataire » ; c'est **+2 a +4** selon la configuration.

Allers-retours REELS (requetes + `SAVEPOINT`), PostgreSQL `bouclepro_test` :

| taille | config | AVANT | APRES | Δ |
|---|---|---|---|---|
| 100 | A — tout coupe | 2 806 | **409** | **−85 %** |
| 100 | B — email seul | 4 406 | 2 612 | −41 % |
| 100 | C — defaut produit | 5 206 | 4 212 | −19 % |
| 200 | A | 5 606 | **809** | **−86 %** |
| 200 | B | 8 806 | 5 212 | −41 % |
| 200 | C | 10 406 | 8 412 | −19 % |

Par destinataire : **28,1 → 4,1** (A), 44,1 → 26,1 (B), 52,1 → 42,1 (C).
Les gains que j'avais annonces (−88 / −42 / −21 %) etaient donc **legerement
optimistes** : les vrais sont **−85 / −41 / −19 %**.

### B. La transaction du producteur est CLOSE avant les envois — prouve par le code

`notifierLaDemandeDAide()` est appele **dans** le `DB::transaction()` de
`sendHelpRequestMessage()`. Une Boucle de 200 membres tient-elle une
transaction Neon ouverte 15 secondes ? **Non**, et la preuve est documentaire :

1. les deux jobs declarent `afterCommit` ;
2. `SyncQueue::push()` l'honore : en transaction il enregistre un rappel aupres
   de `db.transactions` au lieu d'executer le job (`SyncQueue.php:129-155`) ;
3. `Connection::commit()` appelle `$this->getPdo()->commit()` **AVANT**
   `$this->transactionsManager?->commit()`, qui declenche les rappels.

Le commit PostgreSQL a donc lieu d'abord, les envois ensuite — hors
transaction, mais **toujours dans la requete HTTP de l'auteur**.

⚠️ Mon premier instrument mesurait « duree dans la transaction » ≈ duree
totale, ce qui etait faux : `TransactionCommitted` est emis APRES les rappels.
Corrige sur `TransactionCommitting`. Sous `RefreshDatabase` cet evenement n'est
jamais emis (le test est lui-meme une transaction de niveau 1) : la preuve est
**documentaire, pas experimentale**, et c'est dit comme tel.

### C. ⚠️ Je retire « aucun risque de panne »

L'affirmation etait trop large.

| affirmation | statut |
|---|---|
| un echec SMTP ne produit pas de 500 | **PROUVE** — `catch (Throwable)` autour de `Mail::html()` |
| un echec FCM/Push ne produit pas de 500 | **PROUVE** — `catch (\Throwable)` dans `deposer()` |
| une erreur SQL pendant le fan-out ne produit pas de 500 | **FAUX** — `SyncQueue::handleException()` fait `throw $e` (ligne 269). Toute exception non attrapee dans le livreur remonte dans la requete de publication. |
| `$timeout` protege la requete | **FAUX** — `timeout = 60` / `120` sont honores par le **Worker** de file, qui n'existe pas ici. Sous `sync` la seule borne est `max_execution_time` et le delai du proxy Laravel Cloud, **ni l'un ni l'autre mesure**. |

Formulation juste : **les echecs de TRANSPORT sont absorbes ; les echecs de
BASE et l'epuisement du temps mural ne le sont pas** — et c'est le second qui
grandit avec la taille de la Boucle.

### D. La latence transport est le poste DOMINANT, et elle n'a jamais ete mesuree

Le banc l'avait retiree (`Http::fake()` + transport `array`). Ce qui est
determinable **par lecture du code**, sans supposer de RTT :

| canal | reutilisation de connexion | cout par destinataire |
|---|---|---|
| **email** | **oui** — `MailManager::get()` met le mailer en cache, le transport Symfony garde le flux SMTP ouvert | 1 poignee de main pour toute la requete, puis **~3-4 allers-retours protocolaires** par message |
| **Web Push** | **NON** — `Http::withHeaders(...)` fabrique un `PendingRequest` neuf, dont `buildClient()` rend `$this->client ?? createClient(...)` | **une poignee de main TCP + TLS COMPLETE par appareil** (~3 allers-retours) |

Le push paie donc un handshake TLS **par destinataire**. Inefficacite reelle
et corrigeable, **non corrigee ici** : hors du perimetre SQL de cette TASK.

**Pourquoi aucun chiffre PROD n'est donne.** Le systeme enregistre deja
l'intervalle `claimed_at` → `sent_at`, qui encadre exactement l'appel
transport. Deux raisons le rendent inexploitable :

1. **les horodatages sont a la SECONDE** — mediane de l'ecart 0 ms, maximum
   1000 ms : la donnee ne peut pas repondre a une question sub-seconde ;
2. **l'echantillon n'est pas de la PROD** — jumeau `bouclepro_prod_work` :
   45 emails et 10 pushs, dont les plus recents (07/11 00h22) forment une
   rafale de 8 emails en 1-2 s, compatible avec une recette **locale contre
   Mailpit** (`127.0.0.1:1025`), pas avec `relai-smtp.net`.

Ordre de grandeur, explicitement parametre : a 100 destinataires en config C,
100 x (3-4 AR SMTP) + 100 x (3 AR FCM). A 20 ms de RTT → **~13 s** ; a 50 ms →
**~33 s**. Ces secondes **s'ajoutent** aux 7,6 s de SQL+CPU.

Mesure possible, non faite ici car c'est une migration : passer
`claimed_at`/`sent_at` en precision **milliseconde**. Le systeme repondrait
alors de lui-meme, sur des donnees reelles.

### E. Les limites liees a Neon

| limite | effet | statut |
|---|---|---|
| 1 aller-retour par requete **et par `SAVEPOINT`** | **~80 % du temps estime** | RTT de 1,5 ms **estime, non mesure** |
| serverless : veille du calcul apres inactivite | premier acces apres veille paie un reveil | documente par Neon, non mesure ici |
| plafond de connexions simultanees | 2 auteurs publiant ensemble doublent les connexions | non mesure |
| PITR 7 jours | filet de donnees, pas de rollback | acquis le 05/11 |

Le plafond de Starter n'est **ni la RAM** (+4 Mo au pic a 200 membres) **ni le
CPU** (2,8 s a 200 membres) : c'est **le nombre d'allers-retours dans une
requete HTTP**, SQL et transport confondus.

### F. Le verdict, revise

| taille, config C (defaut produit) | SQL+CPU estime | transport (non mesure, a 20 ms de RTT) | total |
|---|---|---|---|
| 20 membres | ~1,3 s | ~2,6 s | **~4 s** |
| 50 membres | ~3,2 s | ~6,5 s | **~10 s** |
| **100 membres (cible POC)** | **~7,6 s** | **~13 s** | **~20 s** |
| 200 membres (plafond) | ~15 s | ~26 s | **~41 s** |

**Le poste dominant n'est pas le SQL que cette TASK a optimise : c'est le
transport, que le banc avait retire.**

L'optimisation reste juste et utile — elle divise par **sept** le cout d'un
membre qui s'est tu, et retire **1 000 allers-retours** a 100 membres — mais
elle **ne suffit pas** a rendre `sync` viable a 100 destinataires. Aucune
optimisation SQL ne l'y rendra viable. La seule mesure qui attaque le poste
dominant est de sortir les envois de la requete de publication : le point 6.

## 5. Managed Queue sur Starter — etude en lecture seule (point 6)

Source : <https://laravel.com/cloud/docs/queues>, lu le 07/11.
**Aucune ressource creee, aucune commande d'ecriture Cloud.**

### L'architecture decrite par MASTER est celle que la doc prescrit, mot pour mot

> « To continue using another driver for some jobs, set `QUEUE_CONNECTION` to
> that driver and dispatch managed-queue jobs explicitly with
> `->onConnection('cloud')`. »

Donc : **`QUEUE_CONNECTION` reste `sync`** — les 4 files sans consommateur
(T1777) continuent de fonctionner sans risque d'arret silencieux — **et seuls
les deux jobs de notification portent `->onConnection('cloud')`**.

⚠️ Piege que cela desamorce, la doc le signale elle-meme :

> « When you deploy a managed queue, Laravel Cloud sets `QUEUE_CONNECTION=cloud`
> for the environment. […] **Any job dispatched without an explicit
> connection** […] routes to a managed queue once one exists. »

Il faut donc **re-epingler `QUEUE_CONNECTION=sync` explicitement** apres la
creation de la file, sinon les 8 jobs y partent — dont les 4 orphelins.

### Ce que Starter autorise, et les deux contraintes qui mordent

| | Starter |
|---|---|
| files managees par environnement | **1** |
| workers maximum par file | 3 |
| classe de calcul | **Flex seulement** (Pro indisponible) |
| memoire | 256 Mio a 2 Gio |
| **duree maximale d'un job (Flex)** | **90 secondes** |

**Contrainte 1 — une seule file, mais deux noms de file.**
`SendNotificationEmail` fait `onQueue('notifications-email')` et
`SendNotificationWebPush` `onQueue('notifications-web-push')`. Or « each
managed queue handles one queue name ». Avec une seule file managee, les jobs
envoyes vers l'autre nom **ne seraient jamais traites** — exactement le mode
d'arret silencieux de T1777. Les deux jobs doivent viser **le MEME nom de
file**. C'est une condition de correction, pas un confort.

**Contrainte 2 — `SendNotificationWebPush` declare `timeout = 120`**, au-dessus
du plafond Flex de 90 s. Pro n'existe pas sur Starter : il faut l'abaisser a
≤ 90 s, ou accepter qu'un push long soit interrompu.

### Prealables de code

| prealable | etat mesure |
|---|---|
| Laravel ≥ **13.19.0** | **13.7.0** → montee de version mineure requise |
| `aws/aws-sdk-php` dans `composer.json` | **ABSENT** ; present en dependance transitive au `composer.lock` (3.380.2) et `Aws\Sqs\SqsClient` **n'est pas chargeable** → `composer require` necessaire |

### Ce que cela resout, et c'est le point

Les envois SMTP et Push **sortent de la requete de publication**. L'auteur ne
paie plus que la planification : de l'ordre de **600 allers-retours a 100
membres au lieu de 4 212**, et **zero aller-retour SMTP ou FCM**. C'est la
seule mesure qui attaque le poste dominant du §3.D.

Et cela leve le defaut qui avait fait ecarter le plan « worker sur le serveur
existant » :

> « Managed queues run on their own compute and **wake on their own** when jobs
> arrive, so jobs keep processing while your environment sleeps. »

L'hibernation n'est plus un probleme.

### Les deux jobs doivent changer de contrat

| point | aujourd'hui | exige par une file managee |
|---|---|---|
| `$tries` | **1** | > 1 — « Design jobs to tolerate **at-least-once** delivery ». Avec `tries = 1`, un worker interrompu perd la notification **en silence**. La prise atomique `pending -> sending` absorbe deja la redelivraison : le terrain est pret. |
| `$timeout` du push | 120 s | ≤ 90 s (plafond Flex) |
| gestion des echecs | `queue:failed` / `queue:retry` | **non supportes** → tableau de bord ou API Cloud |

### Cout, calcule et non suppose

Tarifs de la doc : **1 $ par million d'operations** standard ; dispatch + start
+ delete = **3 operations par job** ; base de long-polling **~0,13 $ par file
et par mois** ; worker Flex **0,00000152 $ la seconde**.

Hypothese de volume, dite explicitement : 5 Organizations, 100 publications par
mois, 100 destinataires, 2 canaux → 200 jobs par publication.

| poste | calcul | montant mensuel |
|---|---|---|
| operations | 100 x 200 x 3 = 60 000 | **0,06 $** |
| secondes de worker | 20 000 jobs x ~0,3 s = 6 000 s | **0,01 $** |
| base de polling | 1 file | **0,13 $** |
| **total** | | **~0,20 $ / mois** |

**Aucune ressource supplementaire, aucune montee d'offre, `relai-smtp.net`
inchange** — la file managee ne touche pas au mailer, elle deplace seulement le
moment ou il est appele.

### Sequence proposee, trois TASKs distinctes

| # | TASK | pourquoi elle est separee |
|---|---|---|
| 1 | monter Laravel 13.7 → ≥ 13.19 + `composer require aws/aws-sdk-php` | une montee de version mineure merite sa propre regression ; aucun comportement produit ne change |
| 2 | aligner les deux jobs : nom de file unique, `$tries > 1`, `timeout` du push ≤ 90 s, `->onConnection('cloud')` | tout est testable AVANT qu'une file managee existe |
| 3 | creer la file managee + **re-epingler `QUEUE_CONNECTION=sync`** + recette | la seule TASK qui ecrit sur Laravel Cloud ; a faire avec Cyril au tableau de bord |

Rien de tout cela n'est entrepris ici.
