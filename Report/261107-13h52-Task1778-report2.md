## 2. Performances — quelles optimisations supplementaires sont REELLEMENT utiles

**Aucune.** Et c'est la comparaison que MASTER demandait qui le dit.

### La decomposition mesuree, a 100 membres en configuration C

PostgreSQL local + Mailpit. Le banc separe desormais les phases
(`MessageSending`/`MessageSent` pour l'email, `RequestSending`/`ResponseReceived`
pour le push, `DB::listen` pour le SQL, le reste par soustraction).

| poste | mesure | part |
|---|---|---|
| **SQL** (3 812 requetes + 400 `SAVEPOINT`) | **1 893 ms** | **~57 %** |
| **CPU** (preparation, rendu, hydratation, chiffrement) | **1 362 ms** | **~42 %** |
| transport email (RTT ~ 0) | 10 ms | 0,3 % |
| depot HTTP du push (simule) | 7 ms | 0,2 % |
| **TOTAL local** | **3 271 ms** | |

L'ecart configuration B → C isole le chiffrement Web Push :
**645 ms pour 100 destinataires**, soit **~6,5 ms chacun** (ECDH P-256 +
AES-GCM). Mesure, pas estime.

### Pourquoi ne pas optimiser le client HTTP

Le Web Push fabrique un client Guzzle **neuf par appareil**
(`Http::withHeaders()` → `PendingRequest` neuf → `buildClient()` rend
`$this->client ?? createClient(...)`, qui n'assigne rien). Chaque push paie
donc une poignee de main TCP + TLS complete.

Mutualiser ce client economiserait, a 100 destinataires et 25 ms de RTT,
**environ 5 secondes sur 25**. Mais :

- **un job = un destinataire** (`SendNotificationWebPush::__construct(string $notificationId)`).
  La mutualisation ne peut donc se faire qu'a l'echelle de la REQUETE, via une
  liaison `scoped` — exactement la mecanique de `ScopedReadCache` ;
- sous une **Managed Queue**, chaque destinataire est un job sur un calcul
  separe : **la mutualisation ne rapporte plus rien du tout**.

Autrement dit : c'est du travail dont la valeur entiere disparait le jour ou la
file managee arrive, et qui ne traite que 5 s des 25 s. **La file, elle, en
retire 24.** Je ne le propose donc pas.

Le seul cas ou cela vaudrait la peine est un destinataire a plusieurs appareils
— `MAX_APPAREILS = 10` — et la base PROD contient **1** abonnement au total.

## 3. Transport — mesures contre estimations, frontiere nette

### SMTP : la connexion EST reutilisee, le cout est 4 allers-retours par email

| fait | statut |
|---|---|
| le mailer est mis en cache pour la requete (`MailManager::get()` rend `$this->mailers[$name] ?? $this->resolve($name)`) | **PROUVE** par lecture de `vendor/` |
| le transport Symfony garde le flux SMTP ouvert ; `ping()`/`NOOP` n'intervient qu'au-dela de 100 s entre deux messages | **PROUVE** |
| par message : `MAIL FROM` (attente 250), `RCPT TO` (250), `DATA` (354), charge + `\r\n.\r\n` (250) — **4 allers-retours bloquants**, sans pipelining | **PROUVE** — `SmtpTransport::doSend()` lignes 209-257 |
| cout CPU du protocole | **MESURE** : 9,9 ms en `array` contre 9,8 ms vers Mailpit pour 100 emails → **~0,1 ms par email** |
| latence vers `relai-smtp.net` | **NON MESUREE**, et non mesurable d'ici |

Le cout SMTP en PROD est donc **de la pure latence** : `4 x RTT` par email.
Aucun remplacement de fournisseur, aucune modification : il n'y a rien a
optimiser cote code.

### Web Push : pas de reutilisation, 3 allers-retours par appareil

| fait | statut |
|---|---|
| un client Guzzle par appel | **PROUVE** (`PendingRequest::buildClient()`) |
| donc TCP + TLS + requete ≈ **3 allers-retours par appareil** | derive du protocole |
| `timeout` HTTP par appel : **8 s** ; jusqu'a **10 appareils** par destinataire | **PROUVE** (`TIMEOUT`, `MAX_APPAREILS`) |
| chiffrement | **MESURE** : ~6,5 ms par destinataire |
| latence vers FCM | **NON MESUREE** |

⚠️ **Exposition reelle** : un service de push lent ou injoignable coute jusqu'a
**8 s par appareil**, en serie, dans la requete de publication. A 13
destinataires d'aujourd'hui avec 1 appareil, c'est 8 s au pire. A 100
destinataires tous equipes, ce serait 800 s — borne par rien d'autre que le
delai du proxy.

### Pourquoi aucun chiffre PROD de latence n'est donne

`member_notification_deliveries.claimed_at` et `sent_at` encadrent exactement
l'appel transport, mais :

1. ils sont horodates **a la seconde** (mediane de l'ecart 0 ms, maximum
   1000 ms) ;
2. l'echantillon du jumeau (45 emails, 10 pushs) vient d'une recette **locale
   contre Mailpit**, pas de `relai-smtp.net`.

**Mesure possible, non faite ici car c'est une migration** : passer ces deux
colonnes en precision milliseconde. Le systeme repondrait alors de lui-meme,
sur des donnees reelles. A ouvrir en TASK si MASTER veut le chiffre.

### Le modele PROD, entierement derive

`SQL x RTT_neon + email x 4 x RTT_smtp + push x 3 x RTT_fcm + CPU mesure`

Cout marginal **par destinataire**, avec `RTT_neon = 1,5 ms` et
`RTT_smtp = RTT_fcm = 25 ms` — **ces deux RTT sont les seuls parametres non
mesures** :

| configuration | SQL | SMTP | FCM | CPU | **total** |
|---|---|---|---|---|---|
| A — tout coupe | 6 ms | — | — | 1 ms | **~7 ms** |
| B — email seul | 39 ms | 100 ms | — | 7 ms | **~146 ms** |
| C — email + push | 63 ms | 100 ms | 75 ms | 14 ms | **~252 ms** |

| taille | config B | config C |
|---|---|---|
| **13 (reel aujourd'hui)** | **~1,9 s** | ~3,3 s |
| 20 | ~2,9 s | ~5,1 s |
| 50 | ~7,3 s | ~12,6 s |
| 100 (cible POC) | ~14,6 s | ~25,2 s |
| 200 (plafond) | ~29 s | ~50 s |

**Plafond de `sync` pour un budget de 10 secondes : ~68 destinataires en
configuration B, ~40 en configuration C.**

## 4. Managed Queue — le chemin minimal et sur, sur Starter

### L'architecture, confirmee par la doc

> « To continue using another driver for some jobs, set `QUEUE_CONNECTION` to
> that driver and dispatch managed-queue jobs explicitly with
> `->onConnection('cloud')`. »

`QUEUE_CONNECTION` reste **`sync`** : les 6 jobs non-notification continuent
exactement comme aujourd'hui, dont les 4 files sans consommateur de T1777.
**Aucun n'a de `$connection` ni d'`onConnection()`** — verifie en T1777 — donc
aucun ne bascule par accident, **a condition de re-epingler
`QUEUE_CONNECTION=sync`** apres la creation de la file (Cloud pose `cloud`
de lui-meme).

### Les huit prerequis demandes, un par un

| # | prerequis | etat |
|---|---|---|
| 1 | Laravel ≥ 13.19 | **13.7.0** → montee mineure requise |
| 2 | `aws/aws-sdk-php` en dependance DIRECTE | **absent de `composer.json`** ; present en transitif (3.380.2) et `Aws\Sqs\SqsClient` **non chargeable** |
| 3 | `timeout` du push et contraintes Flex | `timeout = 120` > **plafond Flex 90 s**. Pro indisponible sur Starter → abaisser a ≤ 90 s |
| 4 | politique `$tries = 1` | **voir ci-dessous : la relever ne sert a RIEN** |
| 5 | statuts `pending`/`sending`/`sent`/`failed`/`ambiguous` | intacts, aucun touche par T1778 |
| 6 | recuperation des livraisons orphelines | **a construire** — voir ci-dessous |
| 7 | observabilite et retour arriere | `queue:failed`/`retry`/`clear` et Horizon **non supportes** → tableau de bord ou API Cloud. Retour arriere : repasser les deux jobs sans `onConnection`, la file se vide puis se supprime |
| 8 | les 6 autres jobs | inchanges sous `sync` |

### Point 4 — pourquoi relever `$tries` ne changerait rien

MASTER a eu raison de l'interdire. La raison est structurelle, et je l'ai
verifiee dans le code :

- `prendre()` n'accepte que la transition **`pending` → `sending`** ;
- un job redelivre trouve `sending`, `prendre()` rend `false`, et le livreur
  **`return` sans bruit** (`NotificationEmailDeliverer:174`,
  `NotificationWebPushDeliverer:88`).

Donc : `$tries = 3` donnerait trois tentatives dont **les deux dernieres ne
pourraient jamais reclamer la livraison**. Elles se retireraient en silence, le
job serait compte « reussi », et la livraison resterait bloquee en `sending`.

**Relever `$tries` ne cree aucun double envoi, et ne repare aucune perte.** Le
vrai sujet est ailleurs.

### Point 6 — la recuperation des orphelines, et pourquoi elle ne doit JAMAIS renvoyer

Une livraison bloquee en `sending` (worker tue, memoire epuisee, exception non
attrapee) n'est plus jamais reprise. C'est la perte silencieuse reelle.

A-t-elle ete envoyee ? **Indecidable.** `EmailLog` n'est ecrit qu'APRES le
retour de `Mail::html()` : son absence prouve que l'appel n'est pas revenu,
pas que rien n'est parti — le processus peut etre mort apres que SMTP a accepte
le `DATA`.

Donc la seule politique qui preserve « **aucun double envoi** » :

> une livraison `sending` dont `claimed_at` depasse un seuil est marquee
> **`ambiguous`**, jamais remise en `pending`, et remontee pour decision
> humaine.

Le statut `ambiguous` existe deja exactement pour cela. La notification in-app,
elle, est de toute facon deja delivree : l'enjeu est un email ou un push
manquant, pas une perte d'information.

### Le decoupage minimal — trois TASKs

| # | TASK | contenu | pourquoi separee |
|---|---|---|---|
| **1** | montee Laravel 13.7 → ≥ 13.19 + `composer require aws/aws-sdk-php` | aucune ligne de logique produit | une montee de version merite sa propre regression |
| **2** | robustesse des deux jobs : `try/catch` sur le livreur push (symetrie avec l'email), `timeout` push ≤ 90 s, nom de file UNIQUE pour les deux, recuperation des orphelines en `ambiguous` | **testable sous `sync`, AVANT qu'une file existe** | c'est la TASK qui rend l'asynchrone sur ; elle a de la valeur meme si la file n'arrive jamais |
| **3** | creer la file managee, re-epingler `QUEUE_CONNECTION=sync`, poser `->onConnection('cloud')`, recette | la **seule** qui ecrit sur Laravel Cloud | a faire avec Cyril au tableau de bord |

Ordre impose : 2 avant 3. Poser `onConnection('cloud')` avant la robustesse
transformerait chaque crash de worker en livraison bloquee.

### ⚠️ CORRECTION — la « mesure transitoire » de ce rapport etait FAUSSE

J'avais ecrit qu'une Boucle depassant 40 membres pouvait voir son **maitre**
couper l'email ou le push, ramenant le cout a 7 ms par destinataire. **Ce
levier n'existe pas.** MASTER l'a releve, et la verification le confirme deux
fois :

1. `NotificationPreferenceController::updateLoopPreferences()` lit et ecrit par
   `forOwner((string) $user->id)` et ne parcourt que `bouclesActives($user)` :
   **chaque reglage appartient au membre qui le pose**. Personne — ni le
   createur de la Boucle, ni un administrateur — ne peut couper une Boucle pour
   les autres.
2. `$collectif` y est **force a `true`** : meme son propre interrupteur general
   n'est plus atteignable depuis l'ecran. Seuls `email` et `web_push` le sont.

Un reglage ne reduit donc **jamais** le fan-out d'une Boucle : il retire un
destinataire, celui qui l'a pose. **Il n'y a aucune mesure transitoire**, et
conformement a la decision de MASTER aucune fonctionnalite n'est ajoutee pour
la remplacer. Le critere « pas de timeout a 100 » reste donc ouvert jusqu'a la
file managee.

**Cause de mon erreur, et elle est corrigee dans le code** : la formule
« maitre de Boucle », employee dans les commentaires de T1775 pour designer
`collective_enabled`, se lit aussi bien « interrupteur maitre » que « le maitre
DE LA Boucle ». J'ai retenu le second sens. Le vocabulaire est remplace partout
par **« l'interrupteur general du membre sur cette Boucle »**, et le docblock de
`LoopNotificationPreference` dit desormais explicitement que personne ne coupe
une Boucle pour les autres.

**NO-GO** uniquement si une Boucle de PROD depasse **40 membres actifs** avant
la file managee. Elle n'en a aujourd'hui aucune au-dessus de 13 — et il
n'existe **aucun** levier pour calmer une telle Boucle apres coup : c'est
pourquoi le chiffre doit etre reconfirme juste avant le GO, et non lu sur un
dump.
